# Applied AI Analytics Platform – ML & Decision Intelligence (Databricks / Fabric Ready)

## Overview

This project demonstrates how to transform raw marketing campaign data into a production-ready analytics and AI decision platform using Databricks, Delta Lake, and PySpark MLlib.

The platform builds a structured KPI and machine learning layer that can be consumed by:

* BI tools (Power BI, dashboards)
* Retrieval-Augmented Generation (RAG) systems
* LLM-based assistants and AI agents
* Web applications and APIs

Public Streamlit application:

https://marketing-ai-platform-alpha.streamlit.app

It serves as a foundation for enterprise AI systems operating on structured business data.

```
Raw marketing data (CSV / Database)
        ↓
Curated table (marketing_clean) – Delta Lake
        ↓
KPI computation layer (PySpark)
        ↓
marketing_kpi (Delta Table / Lakehouse)
        ↓
Machine Learning Layer
    - Explanatory revenue model (RandomForest vs baseline, cross-validated)
    - Pre-launch simulation (budget + channel)
    - Campaign segmentation (KMeans on campaign profile)
    - Agent budget simulation (RandomForest — real-time training)
        ↓
Autonomous Agent Layer (LangGraph + GPT-4o-mini)
    - Natural language query interface
    - Parameterized SQL tools
    - Business recommendations
        ↓
Consumption Layer
    - BI dashboards (Power BI / Fabric)
    - LLM assistants (RAG on structured data)
    - Streamlit web app (5 tabs)
    - APIs and AI agents

## 🔒 Security & Advanced AI Architecture

This platform follows enterprise-grade security standards by decoupling the public interface from the proprietary AI logic:

* **Private AI Submodule**: The core training pipelines and fine-tuning logic (LoRA on TinyLlama 1.1B) are hosted in a **secure private repository**. This protects intellectual property and specific training methodologies while keeping the application code open for demonstration.
* **Modular Integration**: The system uses **Git Submodules** to link the secure backend to this public repository, ensuring a clean separation between the production environment and R&D scripts.
* **Parameter-Efficient Fine-Tuning (PEFT)**: Implementation of **LoRA** (Low-Rank Adaptation) to achieve high-performance results with minimal resource consumption (reducing trainable parameters to ~0.10%).
```

## Machine Learning Layer

### Revenue models — evaluated honestly

Figures from `marketing_kpi` (308 rows, 11 campaigns), PySpark MLlib, **5-fold cross-validation**.

| Model | R² | Median error |
|---|---|---|
| RandomForest **with** `roi` (first version) | 0.84 | 21 % |
| RandomForest without `roi` | 0.81 | 26 % |
| Baseline: orders × average basket | **0.88** | 27 % |
| RandomForest without `roi`, unseen campaigns | 0.57 | 44 % |
| Baseline, unseen campaigns | **0.84** | 34 % |

What this shows:

* The first version reported **R² = 0.95** on a single 80/20 split. It used `roi` as an input, but
  `roi = (revenue − spend) / spend` contains the target (**data leakage**), and a single split of ~50 test rows
  is unstable (R² from ~0.6 to ~0.95 depending on the seed).
* A one-line baseline (`revenue = orders × average basket`) **beats the RandomForest**. The model explains revenue
  after the fact, but cannot simulate a campaign: orders are unknown before launch.

### Pre-launch simulation

Inputs are limited to what is decided **before** launch: **budget** and **channel**.

* RandomForest, cross-validated **R² ≈ 0.63**, median error ≈ 45 %
* Each forecast comes with an empirical range (10th–90th percentile of actual / predicted in cross-validation)
* Influencer brings the most revenue per franc invested, social the least (≈ 27 k vs ≈ 11 k for a 10 k budget)
* Diminishing returns: at 50 k the predicted ROI drops on every channel
* Budgets outside the range observed for a channel are flagged as extrapolation

---

### Budget Simulation (simulate_budget tool)

Model: RandomForestRegressor on **budget + channel only** (`src/app/budget_simulation.py`, shared by the
agent and the Streamlit app) — retrained in real time on Databricks data.

Purpose:

* Simulate the impact of a budget change (−90 % to +300 %) on revenue
* Available per category (social, search, influencer, media, all)

Method: the model never sees clicks or orders (they are outcomes of the budget, not levers).
Effect = predicted revenue at the new budget − predicted revenue at the current budget, added to the observed revenue.
Rows whose new budget exceeds the maximum observed for their channel are reported, since a forest cannot extrapolate.

Output (agent on the live Databricks `marketing_kpi` table):

```
Simulation +20% budget (social):
  Budget actuel     : CHF 13 798 501
  Budget simulé     : CHF 16 558 201
  Revenue actuel    : CHF 11 911 454
  Revenue simulé    : CHF 14 827 957
  Delta revenue     : +CHF 2 916 503 (+24.5%)
  ROAS incrémental  : 1.06 (each extra franc brings 1.06 of revenue)
  ROI incrémental   : +6%
```

### Campaign Segmentation

Model: KMeans on **CTR, CVR, CPL and log(budget)**. Revenue and ROI are **not** used to build the segments,
only to describe them — otherwise clustering simply rediscovers "what worked / what didn't".
KMeans is run with 10 seeds and the best silhouette is kept (a single seed gives different segments depending on row order). k = 4 (silhouette ≈ 0.46) is retained for business reading; k = 2 scores slightly higher but is too coarse to guide budget decisions.

| Segment | Profile | Median ROI |
|---|---|---|
| Small budgets, high CTR | CTR ≈ 5× the rest | ≈ +1.0 |
| Large budgets | highest budgets | ≈ +0.15 to +0.3 |
| Small campaigns, poor conversion | CVR clearly lower | ≈ −0.15 to −0.25 |
| Very high CPL | CPL ≈ 2.7× the rest | ≈ −0.9 |

Since ROI played no part in forming the segments, the ROI gap between them is a genuine finding:
a campaign's profile is enough to spot those that destroy value.

## Autonomous Agent — LangGraph

The platform includes a fully autonomous marketing agent built with **LangGraph** and **GPT-4o-mini**.

### Workflow

```
User question (natural language)
        ↓
route_intent     → kpi_qa | diagnostic | segmentation | budget_simulation
        ↓
plan_tools       → LLM selects 1-2 tools and generates JSON call
        ↓
execute_tools    → Parameterized SQL queries on Databricks SQL Warehouse
        ↓
compose_answer   → Business response in French with 2-4 recommendations
```

### Available Tools

| Tool | Description | Parameters |
|------|-------------|------------|
| `rank_campaigns` | Top/Bottom campaigns by metric | `metric`, `direction`, `limit` |
| `get_underperforming_campaigns` | Campaigns below ROI threshold | `roi_threshold`, `limit` |
| `aggregate_by_dimension` | KPI aggregation by category | `group_by` |
| `simulate_budget` | RandomForest budget simulation | `budget_increase_pct`, `category` |

### Security

* Parameterized SQL queries (SQL injection prevention); `simulate_budget` runs a fixed query and validates
  the category against the values present in the data
* Whitelisted table: `marketing_kpi` only
* Forbidden operations: `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`
* Whitelisted metrics: `roi`, `revenue`, `ctr`, `cvr`

## RAG (Retrieval-Augmented Generation) Integration

## Notebook

Core implementation:

```
Notebooks/01_marketing_kpi_revenue_prediction.ipynb
```

Key steps:

* Load marketing_clean dataset
* Compute KPI metrics (CTR, CVR, CPL, ROI) and save the `marketing_kpi` Delta table
* Evaluate revenue models with cross-validation against a baseline
* Simulate a campaign before launch (budget + channel) with a range
* Segment campaigns by profile (KMeans, silhouette)

The notebook runs on **Databricks** (including serverless / Free Edition: no `df.cache()`, Spark Connect-safe model handling, ANSI-safe divisions) and on Microsoft Fabric. The source table is `marketing_clean` (or `marketting_clean`, the name used in the Databricks workspace); if neither exists, it starts from `marketing_kpi`. `marketing_kpi` is only overwritten when every one of its current columns is recomputed, so the agent and the Databricks dashboards cannot break.

## 🧬 Fine-Tuning LoRA

TinyLlama 1.1B fine-tuned with LoRA (PEFT/TRL) on 500+ proprietary marketing KPI examples.

**Model on HuggingFace Hub:** [Doers97/marketing-lora-tinyllama](https://huggingface.co/Doers97/marketing-lora-tinyllama)

**Live inference:** Hugging Face Space [Doers97/marketing-lora-demo](https://huggingface.co/spaces/Doers97/marketing-lora-demo)
(code in `hf_space/`). The Streamlit tab calls its `/recommend` API with `gradio_client`; the prompt reproduces the
training format exactly. If the Space is asleep or unavailable, the tab falls back to business rules using the same
thresholds as the training labels (ROI > 150 % → scale, 30–150 % → optimize, < 30 % → review).

| Metric | Value |
|--------|-------|
| Technique | LoRA (r=8, alpha=16) |
| Trainable params | 0.10% (1.1M / 1.1B) |
| Val loss | 0.24 |
| Training time | 5 min — T4 GPU (Google Colab) |

Example inference:
- ROI = -20% → `REVIEW immediately` ✅
- ROI = +381% → `SCALE immediately` ✅
